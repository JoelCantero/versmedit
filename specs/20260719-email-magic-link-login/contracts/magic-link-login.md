# Interface Contract: Email Magic Link Login

## Localized Page Contract

| Method | Route | Locale | Purpose |
|---|---|---|---|
| `GET` | `/login` | English | Render email-only login |
| `GET` | `/es/login` | Spanish | Render email-only login |
| `GET` | `/ca/login` | Catalan | Render email-only login |
| `GET` | `/login/error` | English | Render invalid-link recovery |
| `GET` | `/es/login/error` | Spanish | Render invalid-link recovery |
| `GET` | `/ca/login/error` | Catalan | Render invalid-link recovery |

All visible text comes from the active next-intl catalog. Login pages expose one labeled email input
and one primary action. They expose no password, name, social-provider, or registration control.

## Obtain CSRF Token

The page obtains a NextAuth-compatible CSRF token through the existing Auth.js page/server boundary.
The browser receives the corresponding HTTP-only/same-site cookie. A sign-in request is processed
only when body token, cookie token, and cookie signature match.

## Request Magic Link

`POST /api/auth/signin/email`

This API route is intentionally not localized. It is public but protected by canonical-host checks,
double-submit CSRF, shared rate limits, strict validation, and uniform account-independent outcomes.

### Request

Content type: `application/x-www-form-urlencoded`

| Field | Required | Rules |
|---|---|---|
| `csrfToken` | Yes | Valid NextAuth double-submit token |
| `email` | Yes | Trimmed/lowercased server-side; valid email; maximum 254 chars |
| `callbackUrl` | Yes | Server/page-provided canonical locale home only |
| `json` | Yes | Literal `true` so the client receives JSON rather than navigation |

The server derives client identity from the request through the existing proxy policy. No client ID,
account ID, user ID, or locale authority is accepted from the request body.

### Accepted Response

Status: `200 OK`

```json
{"status":"accepted"}
```

This exact status and body apply to all of the following:

- known valid email with accepted delivery;
- unknown valid email;
- known valid email with isolated recipient/delivery failure after exact-token cleanup;
- any other accepted outcome that must not reveal account existence.

No `Location` header or account-dependent header is returned. The client displays exactly the active
locale's generic confirmation from the message catalog. Every accepted outcome waits until a common
request-start-relative floor of 500 ms plus server-selected jitter of 0–100 ms has elapsed.

### Invalid Email Response

Status: `400 Bad Request`

```json
{"status":"invalid","field":"email"}
```

The client counter has been consumed. No address counter, account lookup, token, or email occurs.

### Invalid CSRF/Request Response

Status: `403 Forbidden`

```json
{"status":"invalid_request"}
```

The client limit has already been consumed. This response occurs before account lookup and is
independent of the submitted email. The client presents the localized invalid-request state and
requires a fresh page/CSRF token; it MUST NOT present provider unavailability.

### Rate-Limited Response

Status: `429 Too Many Requests`

Headers:

```text
Retry-After: <positive whole seconds>
X-RateLimit-Remaining: 0
```

```json
{"status":"rate_limited","retryAfter":<same whole seconds>}
```

Client limits are checked first. If the client is blocked, no address bucket is consumed. Valid known
and unknown addresses have identical address-limit behavior.

### Provider-Unavailable Response

Status: `503 Service Unavailable`

Optional header when a cooldown expiry is known:

```text
Retry-After: <positive whole seconds>
```

```json
{"status":"unavailable"}
```

This response is returned only while the shared global provider marker is active, before account
lookup, and therefore applies identically to every valid known or unknown address. A request that
first detects a provider-wide transport failure still receives the accepted response; it sets the
marker for later requests.

### Response Privacy Rules

- Accepted known/unknown responses are compared as raw status, body, and observable redirect/header
  behavior in integration tests.
- Responses never contain an email, user/account existence flag, token, callback URL, SMTP detail,
  or delivery result.
- Logs may contain request ID, route, coarse status category, limit type, and retry duration only.

## Magic Link Callback

`GET /api/auth/callback/email?callbackUrl=<canonical>&token=<raw>&email=<normalized>`

The URL is generated by Auth.js and delivered only for existing accounts. It is confidential and
must not be logged.

### Successful Callback

- Atomically consumes the matching hashed token.
- Establishes the existing database-backed Auth.js session.
- Redirects to the locale home encoded by the server-approved callback path:
  `/`, `/es`, or `/ca`.
- A second/concurrent use cannot establish another session.

### Rejected Callback

Missing, malformed, expired, superseded, delivery-failed, or already-used tokens do not authenticate.
They redirect to the matching localized login error route, which always uses the generic
`invalidLink` presentation and never claims a specific cause. No foreign callback origin is followed.

## Accessibility Contract

- Email label is programmatically associated with its input.
- Invalid state uses `aria-invalid` and an associated error description.
- Pending disables submit and announces sending without moving focus unexpectedly.
- Accepted, invalid-request, limited, unavailable, and invalid-link states use suitable live-region semantics.
- Keyboard order follows document order; every interactive control has visible focus.
- Reserved message/status space prevents unexpected layout movement between required states.
